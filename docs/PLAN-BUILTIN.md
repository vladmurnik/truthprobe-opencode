# План: TruthProbe на встроенных моделях OpenCode (этап E)

Решение пользователя: сначала фича должна работать на **встроенных моделях opencode** (без
своих ключей), а сторонние API люди допишут сами через расширяемый слой.

Источник фактов: `packages/core/src/models-dev/snapshot.txt` (провайдер `opencode`, 150 моделей)
и код `packages/ai/src/protocols/*` в клоне `sst/opencode@007afb1`.

---

## 1. Что есть на входе (измерено, не предположения)

Провайдер `opencode` (Zen/Console), 150 моделей, шесть API-семейств:

| Семейство | Моделей | Base URL | logprobs технически возможны |
|---|---:|---|---|
| `chat-completions` (OpenAI-compatible) | **69** | `opencode.ai/inference/openai/v1` | **да** — единственное подходящее |
| `responses` (OpenAI Responses) | 37 | `opencode.ai/inference/openai/v1` | нет (Responses API не отдаёт token logprobs) |
| `messages` (Anthropic) | 25 | `opencode.ai/inference/anthropic/v1` | нет |
| `generate-content` (Google) | 12 | `opencode.ai/inference/google/v1beta` | нет |
| `systemone` (decisions) | 4 | `opencode.ai/inference/systemone/v1` | нет |
| `images` | 4 | — | не применимо |

**Главный технический вывод:** `packages/ai/src/protocols/openai-compatible-chat.ts` — тонкая
обёртка, которая *«reuses `OpenAIChat.protocol` end-to-end and overrides only the route id»*.
Значит **один патч в `openai-chat.ts` автоматически покрывает все 69 chat-completions моделей
встроенного провайдера** — включая все `-free`. Отдельный код под каждую модель не нужен.

Бесплатные модели на подходящем протоколе (кандидаты в демо «из коробки»):
`longcat-2.5-free`, `glm-5-free`, `glm-4.7-free`, `deepseek-v4.1-flash-free`,
`mimo-v2.6-flash-free`, `ling-2.6-flash-free`, `ll-alpha-free`, `beam-free`, `exo-free`,
`trinity-large-preview-free`, `nemotron-3.5-super-vl-free`.

## 2. Единственное настоящее неизвестное

Встроенный провайдер — это **шлюз** (`opencode.ai/inference/...`), а не прямой вендорский API.
Шлюз вправе: (а) пробросить `logprobs`/`top_logprobs` как есть; (б) вернуть 400 на неизвестные
поля; (в) молча проигнорировать и не вернуть `logprobs` в ответе. Поведение надо **измерить**,
а не угадывать, причём отдельно по каждой модели (апстрим у моделей разный: vLLM/SGLang отдают,
некоторые провайдерные реализации — нет).

Поэтому этап E начинается с пробы, а не с кода UI.

## 3. Проба возможностей (E1)

`scripts/probe-logprobs.py` — по каждой модели из chat-completions:

```
POST {base}/chat/completions
{ "model": <id>, "messages": [{"role":"user","content":"Say OK"}],
  "max_tokens": 1, "logprobs": true, "top_logprobs": 5, "stream": false }
```

Классификация ответа:

| Наблюдение | Статус | Что делаем в UI |
|---|---|---|
| 200 + `choices[0].logprobs.content[]` непустой | `ok` | полный режим L1+L2+L3 |
| 200, но `logprobs` = null/отсутствует | `ignored` | бейдж «шлюз не отдаёт вероятности» + режим `verbalized` |
| 400/422 с упоминанием logprobs | `rejected` | фича молча выключена для модели |
| 401/403/429 | `auth`/`rate` | не кэшируем, повторяем позже |

Результат — `~/.local/share/opencode/truthprobe/capabilities.json`:

```jsonc
{ "version": 1, "probedAt": "2026-11-19T12:00:00Z",
  "providers": { "opencode": {
    "deepseek-v4.1-flash-free": { "status": "ok", "topK": 5, "latencyMs": 240 },
    "gpt-5.2-codex":            { "status": "skipped", "reason": "responses api" } } } }
```

Правила: TTL 7 дней; проба ленивая (при первом ответе модели) и по кнопке
`/truthprobe probe`; параллелизм ≤ 4, чтобы не ловить 429; результат переиспользуется всеми сессиями.

**DoD E1:** файл заполнен для всех 69 моделей, есть таблица «сколько `ok` / `ignored` / `rejected`»
в `docs/CAPABILITIES.md` (файл ещё не создан — артефакт этапа E1). Это и есть ответ на вопрос «а на встроенных моделях вообще сработает?».

## 4. Что делаем при `ignored` — режим verbalized (E5)

Честная деградация: тот же ответ, но сигнал другой природы — модель сама оценивает уверенность
по каждому предложению (просьба вернуть JSON `[{i, confidence}]`). Помечаем иконкой «самоотчёт»,
не смешиваем с logprob-скорингом и **не** выдаём за измерение. Причина: по arXiv 2305.14975 у
RLHF-моделей вербализованная уверенность часто калибрована лучше условных вероятностей, но это
другой сигнал, и путать их в одном числе нельзя.

## 5. Слой расширяемости под свои API (E6)

Цель: человек добавляет провайдера **дескриптором в конфиг, без правки кода**.

```jsonc
// ~/.config/opencode/truthprobe.json
{
  "mode": "summary",
  "topK": 20,
  "adapters": {
    "vllm-local": {
      "protocol": "openai-chat",           // переиспользуем существующий парсер
      "baseURL": "http://127.0.0.1:8000/v1",
      "request": { "logprobs": true, "top_logprobs": 20 },
      "response": { "path": "choices[0].logprobs.content[]",
                    "token": "token", "logprob": "logprob", "top": "top_logprobs" }
    },
    "custom-jsonl": {
      "protocol": "custom",
      "request": { "return_logits": true },
      "response": { "path": "tokens[]", "token": "t", "logprob": "lp", "top": "alternatives" }
    }
  }
}
```

Контракт адаптера — 4 вещи: (1) как попросить, (2) где в ответе лежит список токенов,
(3) имена полей токена/логпроба/альтернатив, (4) как считать энтропию (top-K или только p).
Всё остальное (сегментация, формулы, пороги, UI) — общее. Это и есть «люди допишут под свои API».

Валидация: неизвестный `protocol` → предупреждение, фича выключена; битый `path` → статус
`parse-error` в бейдже, а не падение сессии.

## 6. Этапы и порядок

| ID | Работа | DoD |
|---|---|---|
| **E1** | Проба 69 моделей `chat-completions` на шлюзе Zen | `docs/CAPABILITIES.md` (пока не создан) с реальными статусами и числами |
| **E2** | Патч протокола: `logprobs`/`top_logprobs` в `bodyFields` + гейт в `fromRequest` | снапшот-тест: тело запроса меняется только при `status: ok`; Anthropic/Gemini не тронуты |
| **E3** | Парсинг дельт + перенос в `providerMetadata` → `session.text.scored` | фикстуры OpenAI/DeepSeek/GLM; отсутствие поля не ломает стрим |
| **E4** | Скоринг + хранение в части сообщения (`AssistantText.truthprobe`) | unit-тесты зелёные, reload сессии сохраняет оценку |
| **E5** | UI: строка до ответа (первое предложение) + блок после + подсветка флагами | ручной прогон в VM на 3 бесплатных моделях, скриншот |
| **E6** | Деградация `ignored`/`rejected` + вербализованный режим | на claude/gemini честное «недоступно», ничего не падает |
| **E7** | Адаптеры сторонних провайдеров по конфигу | vLLM локально/через туннель — работает без правки кода |

Порядок жёсткий: E1 → E2 → E3 → E4 → E5, затем E6/E7 параллельно.

## 7. Критерии приёмки этапа

1. На ≥3 бесплатных встроенных моделях видно: уверенность первого предложения до текста,
   агрегат после, помеченные спорные предложения.
2. На `claude-*`, `gemini-*`, `gpt-5.x/6.x` (responses) — состояние «недоступно», без поломки
   ответа и без 400-х.
3. Ни одна модель не деградирует по скорости больше чем на ~5% (замер на 5 запросах).
4. Добавление нового провайдера = правка одного JSON, перезапуск не нужен.
5. `bun test` зелёный; сборка `packages/core` и `packages/tui` проходит.

## 8. Риски этапа и ответы

| Риск | Проверяем | Если сработал |
|---|---|---|
| Шлюз Zen вырезает logprobs у всех 69 | E1 | остаёмся на режиме verbalized + свой ключ/локальная модель как «точный» режим |
| Бесплатные модели идут с `temperature` > 0 | E1 (temp из snapshot) | помечаем оценку как шумную (`status: partial`), не строим на ней выводы |
| `top_logprobs` ограничен (например, 5) | E1 | φ_first считаем по доступному K, `topK` берём из пробы |
| Разные апстримы в одном шлюзе ведут себя по-разному | E1 | статус **на модель**, не на провайдера |
| Оценка «уверенно» на выдумке | E6 калибровка | показываем «риск», а не «правда»; список спорных предложений — главный выход |

## 9. Оценка трудозатрат

E1 — 0.5 дня (скрипт + прогон + отчёт), E2–E4 — 1 день, E5 — 1 день, E6–E7 — 0.5 дня.
Итого ~3 дня, из них первый день даёт ответ «работает ли это на встроенных моделях вообще».
