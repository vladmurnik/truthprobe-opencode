## 1. Цель

Показать пользователю OpenCode, **насколько модель уверена в том, что говорит**, опираясь на
вероятности первых токенов, а не на самоотчёт модели.

Три уровня вывода — по возрастанию сложности:

| # | Что видит пользователь | Источник сигнала |
|---|---|---|
| L1 | Строка **перед** ответом: уверенность в первом предложении | `φ_first` первого содержательного токена |
| L2 | Блок **в конце** ответа: агрегированная уверенность по всему ответу + число спорных предложений | геом. среднее вероятностей токенов, среднее по предложениям |
| L3 | **Подсветка** конкретных спорных предложений прямо в тексте | min/mean logprob + энтропия на старте предложения |

### Не-цели

- Не доказывать «правду» как факт. Выход — **калиброванный риск**, не вердикт.
- Не заменять и не переопределять проверку тулами/тестами: код проверяется компилятором, а не logprobs.
- Не блокировать ответы модели (v1 — только индикация; блокировка возможна позже как политика).
- Не поддерживать провайдеров без token logprobs (Anthropic, Gemini) — для них честный статус `unavailable`.
- Не реализовывать semantic entropy / SelfCheckGPT-сэмплирование в v1 (дорого, отдельный этап).

## 2. Ключевое ограничение, определяющее всю архитектуру

OpenCode **не запрашивает и не хранит** logprobs. Проверено по дереву `sst/opencode@dev`
(12 659 файлов): совпадений по `logprob` — ноль, включая `@opencode-ai/plugin` d.ts.
Значит плагином (hook-only) задачу не решить → **патчим ядро**, как выбрано (вариант B).

Что это влечёт:

1. `logprobs: true` + `top_logprobs: K` нужно добавить в запрос на уровне провайдера.
2. Нужно научиться парсить `choices[].logprobs.content[]` из стрима (OpenAI-совместимый формат).
3. Нужно место хранения: metadata части сообщения (переживает reload сессии, доступна плагинам).
4. Нужно отрисовать: TUI-рендер текста + строка-статус.

## 3. Провайдерская матрица (гейт возможностей)

| Провайдер | logprobs | top_logprobs | Примечание |
|---|---|---|---|
| OpenAI (chat completions) | да | да | эталонный формат |
| DeepSeek (OpenAI-совместимый) | да | да | основной тестовый провайдер |
| Groq / vLLM / llama.cpp | да | да | удобно для оффлайн-тестов |
| Anthropic, Gemini | **нет** | — | фича должна деградировать, а не ломать запрос |

Правило: параметр добавляется только если `model.capabilities.logprobs === true` **и** включён
конфиг. Иначе — ничего не отправляем (иначе провайдер вернёт 400).

## 4. Архитектура и поток данных

```
user turn
  └─ session/prompt
      ├─ provider.request  ──[+ logprobs, top_logprobs: K]──> API
      │        stream chunks ──> ParseLogprobs ──> TokenBuffer (per messageID)
      │                                              │
      │                        SentenceSegmenter <────┘
      │                                │
      │                          Score (φ_first, per-sentence, whole-answer)
      │                                │
      ├─ part.text.metadata.truthprobe ─┤   (persisted, schema-extended)
      ├─ event "truthprobe.scored"  ────┤   (для плагинов/скриптов)
      └─ TUI render: badge before / block after / inline highlight
```

### 4.1 Схема данных (metadata части)

```jsonc
{
  "truthprobe": {
    "version": 1,
    "status": "ok" | "unavailable" | "partial",
    "model": { "providerID": "deepseek", "modelID": "deepseek-chat", "topK": 20 },
    "answer": { "score": 0.87, "risk": 0.13, "sentences": 14, "flagged": 2 },
    "first":  { "score": 0.94, "entropy": 0.11, "token": "T", "text": "The statement is true." },
    "sentences": [
      { "i": 0, "start": 0, "end": 18, "score": 0.94, "risk": 0.06, "minLp": -0.02, "flag": false },
      { "i": 7, "start": 412, "end": 470, "score": 0.41, "risk": 0.59, "minLp": -1.83, "flag": true }
    ]
  }
}
```

Токены не сохраняем целиком (объём): храним агрегаты по предложениям + первый токен.
Сырые токены — только при `truthprobe.debug = true`.

### 4.2 Метрики (точные формулы)

Пусть для токена `t` есть `lp_t = log p(t)` и распределение top-K `{q_1..q_K}`.

- **Нормированная энтропия**: `H = -Σ q_i log q_i / log K`, `H ∈ [0,1]` (если top-K не пришёл — `H = 1 - exp(lp_t)`).
- **Уверенность первого токена**: `φ_first = 1 − H_1` по первому содержательному токену
  (пропускаем markdown/пунктуацию/пробелы, код и цитаты — по списку игнорируемых).
- **Предложение** `s` из `n_s` содержательных токенов:
  - `g_s = exp( (1/n_s) Σ lp_t )` — геометрическое среднее вероятностей;
  - `φ_s = 1 − H_{first(s)}`;
  - `score_s = 0.5·g_s + 0.5·φ_s`, `risk_s = 1 − score_s`.
- **Весь ответ**: `score = 0.6·exp(mean lp по всем токенам) + 0.4·mean(score_s)`.
- **Флаг**: `flag_s = risk_s ≥ threshold_risky` (по умолчанию `0.45`, калибруется в T8).
- **Веса**: содержательные токены = не пробелы, не пунктуация в начале предложения,
  не внутри ``` code fence```, не URL.

Все формулы — чистые функции в отдельном модуле, без I/O, чтобы покрыть юнит-тестами
на записанных фикстурах.

## 5. UI-контракт

Инвариант: **ничего не вставляем в текст ответа** (иначе ломаем копипаст и парсинг).
Строки живут в отдельном слое отрисовки.

- **L1 (до/в начале ответа)** — приглушённая строка над первым блоком текста:
  `⚑ уверенность 0.94 · первое предложение: «Утверждение верно.»`
  `status: unavailable` → `⚑ уверенность недоступна (провайдер не отдаёт logprobs)`.
- **L2 (после ответа)** — блок:
  ```
  ⚑ TruthProbe   ответ 0.87 · риск 0.13 · спорных предложений: 2
     ├ #8  0.41  «...»
     └ #12 0.38  «...»
  ```
- **L3 (inline)** — спорные предложения получают префикс `▍` и приглушённо-красный стиль
  (ANSI truecolor, fallback на `red`/dim). Никаких emoji внутри текста, только стиль.

Переключатели: `truthprobe.mode: "off" | "summary" | "full"` (default `summary` = L1+L2).

## 9. Риски и что с ними делаем

| Риск | Влияние | Митигация |
|---|---|---|
| RLHF-модели плохо калиброваны: логпробсы не равны правде (arXiv 2305.14975) | ложное спокойствие на «уверенной лжи» | показываем риск, а не «правду»; в L2 явно «спорных: N»; T8 меряет именно false-confident кейсы |
| Один сигнал коллапсирует к «всё ок» на длинных ответах (arXiv 2606.24420) | бесполезность в кодинг-чатах | фьюжн 3 сигналов (per-token lp, φ на старте предложения, разброс по предложениям); позже — disagreement между двумя проходами |
| `temperature > 0` → top_logprobs шумят | скачущие оценки | фиксируем `temperature` для запроса скоринга либо помечаем `status: "partial"` |
| top-K нет в ответе (часть провайдеров) | fallback | `H = 1 − exp(lp)`, статус `partial` |
| Стоимость: доп. поле увеличивает ответ | трафик | `top_logprobs` ≤ 20, храним агрегаты, не токены |
| TUI-подсветка ломает перенос строк/копипаст | UX | стиль без вставки символов в буфер; `▍` только в отображении |

## 10. Rollback

Фича за флагом → выключение = `truthprobe.mode = "off"`, без отката кода.
Полный откат — `git revert` одного PR; схема metadata аддитивная и optional, миграции не нужны.

## 11. Стратегия жизни патча при обновлениях upstream

Короткий ответ: **да, при форке патч придётся обновлять**, но объём работы управляем — если
держать его аддитивным, за флагом и изолированным в отдельном модуле. Полный набор подходов:

| Подход | Переживает обновления | Цена | Вердикт |
|---|---|---|---|
| A. Плагин-оракул (свой запрос с `max_tokens:1`) | **без изменений** — публичный API плагинов | не видит логпробсы реального ответа, только «переспрос» | оставить как fallback |
| B. Форк + патч ядра | нет, нужен rebase | 7 файлов, из них 1 «горячий» | **текущий выбор** |
| C. Upstream PR в `sst/opencode` | после мёржа — 0 работы | ревью, сроки, не факт что примут | цель после стабилизации |
| D. Локальный прокси-сидекар (MITM между opencode и API) | почти без изменений | хрупко к формату запросов, часть данных теряется | резерв |

Как минимизируем боль от B:

1. **Всё аддитивно.** Ни одного изменённого поведения по умолчанию: новые поля `optional`,
   фича выключена (`truthprobe.mode = "off"`). Такие правки почти не конфликтуют.
2. **Изоляция кода.** Скоринг целиком в новом каталоге `packages/core/src/truthprobe/` —
   конфликтов там не бывает по определению, модуль переживает rebase целиком.
3. **Тонкие швы.** Касаемся ровно 6 мест точечно (по 1–5 строк): `bodyFields` + `fromRequest`
   в `openai-chat.ts`, опциональное поле в `AssistantText`, опциональное поле в `Text.Ended`,
   один `case` в `publish-llm-event.ts`, один обработчик в `message-updater.ts`, один блок в
   `message-parts.tsx`. Самый «горячий» файл — `openai-chat.ts` (там чаще всего правки upstream).
4. **Патч как серия коммитов**, а не один гигантский diff: `01-schema`, `02-protocol-request`,
   `03-protocol-parse`, `04-core-score`, `05-tui`. При конфликте отваливается ровно один слой.
5. **CI-rebase-сторож**: раз в сутки `git fetch upstream && git rebase upstream/dev` в ветке
   `feat/truthprobe`; упало — приходит уведомление. Так вы узнаёте о поломке в день выхода
   релиза, а не через месяц.
6. **Версия прибита**: пока патч не влит наверх, работаем на зафиксированном коммите
   (`007afb1`), а не на `latest` — обновление это осознанное действие, а не сюрприз.
7. **Путь миграции на C**: если PR приняли — удаляем свои коммиты, остаётся только плагин
   отображения; если нет — патч живёт как серия из 5 файлов-коммитов и обновляется за
   ~15–30 минут ревью конфликтов на релиз.

Что это значит на практике: при каждом обновлении opencode вы запускаете
`scripts/apply-patch.sh` (rebase + сборка + тесты), и если он зелёный — ничего делать не нужно.
